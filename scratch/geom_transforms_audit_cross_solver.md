`refactor/operator-strategy-layers` — the main session committed 10 quadrature

## Headline

**No module in the non-SN scope builds a rotation or reflection MATRIX.**
`np.cos` / `np.sin` / `np.arctan2` / `np.arccos` appear on exactly **five
lines** in all of `moc/`+`mc/`+`cp/`+`diffusion/`+`homogeneous/`
(`moc/quadrature.py:89`, `moc/geometry.py:319-320`, `mc/solver.py:412-413`).
Every geometric transformation in this scope is spelled as **angle arithmetic
+ a nearest-neighbour SEARCH**, as an **arithmetic sign in an optical-distance
formula**, or as **modulo wrapping**. The group element is never named.

The three highest-value findings, up front:

1. **MoC `_reflected_azi_index`** (`orpheus/moc/geometry.py:222-229`) computes
   φ → π − φ by angle arithmetic and then finds the partner index with
   `np.argmin(np.abs(phi - phi_refl))` — a hand-rolled, guard-free,
   non-bijective version of `_orbit_closure`'s permutation-building step
   (`orpheus/numerics/symmetry.py:1383-1407`). For the shipped MoC azimuthal
   set the answer is the **closed-form permutation `k → n_azi − 1 − k`**, i.e.
   `[::-1]` — measured exact, see §Measurements.
2. **MoC's azimuthal set IS a set of roots of unity** and is generated by
   `np.linspace` + `np.cos`/`np.sin` — the precise anti-pattern
   `orpheus/numerics/roots_of_unity.py` was written to remove.
   `phi_k = π(k+½)/n_azi = 2π(2k+1)/(4·n_azi)` ⟹
   `roots_of_unity(2*np.arange(n)+1, 4*n)` reproduces it (measured below).
3. **CP's `gap_c = bnd_pos[i] + bnd_pos[j]`** (`orpheus/cp/solver.py:276` and
   `:354`) is the **method of images** — the reflection `s → −s` of the optical
   coordinate through the origin plane — spelled as an *addition instead of a
   subtraction*. The reflecting plane is never named; the only marker is a
   three-word comment.

## TWINS — the same operation implemented twice

Only claims where I checked the math is the *same operation*, not merely
similar-looking. Both `file:line`s cited.

### TWIN 1 (STRONGEST) — the reflection-partner permutation, hand-rolled

- **`orpheus/moc/geometry.py:222-229`** `_reflected_azi_index` — applies
  σ: φ ↦ π − φ to one node, then locates the image among the nodes with
  `np.argmin(np.abs(phi - phi_refl))`.
- **`orpheus/numerics/symmetry.py:1383-1407`** `_orbit_closure` — applies an
  operator to ALL nodes (`moved = nodes @ M.T`), locates every image with
  `pi = np.argmin(dist, axis=1)`, and returns the permutation as an
  `OrbitCertificate`.

Same operation: *build the index permutation a reflection induces on a node
set*. `_orbit_closure` is the general form; `_reflected_azi_index` is the
1-node, 1-operator special case. The differences are **all guards MoC lacks**:

| | `_orbit_closure` (symmetry.py) | `_reflected_azi_index` (moc) |
|---|---|---|
| distance window | `dist > atol*100 → None` (`symmetry.py:1395`) | none — argmin always returns something |
| bijectivity | `np.unique(pi).size != n → None` (`symmetry.py:1401`, ERR-073) | none |
| weight equality | `\|w[pi] − w\| > atol → None` (`symmetry.py:1403`) | none |
| output | the whole permutation, reusable | one index, recomputed per call |

The third-party corroboration: **`orpheus/numerics/symmetry.py:911-940`**
`_is_reflection_invariant_1d` asks *literally the MoC question* — "for each
node x, find the reflected partner −x and check the weights match" — on a 1-D
node array, and it DOES carry an explicit `atol*10` window (`symmetry.py:936`).
MoC's φ-array is a 1-D node array. The two are the same problem.

### TWIN 2 (STRONGEST) — the circular node set ⚠ *upgraded mid-dispatch*

- **`orpheus/moc/quadrature.py:89`** —
  `phi = np.linspace(0, np.pi, n_azi, endpoint=False) + np.pi/(2*n_azi)`,
  consumed as `np.cos`/`np.sin` at **`orpheus/moc/geometry.py:319-320`**.
- **`orpheus/numerics/roots_of_unity.py:156-262`** `roots_of_unity(p, q)` —
  cos/sin of `2πp/q` generated by the group action.
- ⚠ **`orpheus/numerics/quadrature/rules_circle.py:180-287`**
  `periodic_trapezoid(n, shift=STAGGERED)` — landed at commit `647ece5a`
  **during this dispatch**. Line 274 is
  `cos_phi, sin_phi = roots_of_unity(b*np.arange(n) + a, b*n)`.

The twin is not merely "the primitive exists" — **the exact rule exists.**
Algebraically `φ_k = π(k+½)/n_azi = 2π(2k+1)/(4·n_azi)`, so MoC's set is
`roots_of_unity(2k+1, 4·n_azi)`, which is precisely the **upper half of
`periodic_trapezoid(2·n_azi, shift=STAGGERED)`** — the `[0,π)` quotient MoC's
own docstring describes ("the supplementary angle `φ+π` … the same physical
track traversed in the opposite direction", `moc/quadrature.py:41-42`).
Measured over `n_azi ∈ {2,3,4,5,6,8,12,16,32,64}` (M5 below): identical node
sets to ≤`5.0e-16`; the only other difference is the weight normalisation
(MoC `Σω = 1`, the circle rule `Σw = 2π` over the full circle — ratio exactly
`π`). The `numerics` rule has the mirror `k ↦ n−1−k` **bit-exact at every
`n_azi`**; MoC's has it at **none**.

`rules_circle.py`'s own header states the general form of the finding:
"a node set defined by a symmetry group must be produced by the group's
action … `np.sin(np.pi)` is `1.22e-16`; a fold whose singular set is defined
by a tolerance around that is a fold whose well-posedness condition is a
tuning parameter" (`rules_circle.py:126-136`). `moc/quadrature.py:89` is a
live instance of exactly that, and `rules_circle.py:145-147` already names a
second one inside `numerics` itself (`product_mu_phi`'s azimuthal factor,
"today still welded in as `linspace`") — so this is a **three-site** pattern,
two in `numerics`/SN scope and one in MoC.

### TWIN 4 — the method of images / the reflection-orbit Neumann sum

Four independent spellings of "sum the contributions over the orbit of the
reflection group":

1. **`orpheus/cp/solver.py:276-280`** (slab) and **`:353-357`** (radial) —
   `gap_c = bnd_pos[i] + bnd_pos[j]`: the single image term, spelled as an
   addition. (One bounce only; the higher orbit is folded into the white-BC
   factor below.)
2. **`orpheus/cp/solver.py:389-395`** `_apply_white_bc` —
   `P_inf += outer(P_out, P_in)/(1 − P_inout)`: the rank-1 geometric series
   over the re-entry orbit.
3. **`orpheus/derivations/continuous/peierls_nystrom/geometry.py:2300-2310`
   (+ `:5904` `_build_specular_multibounce_op`)** —
   `K_bc = G·R·(I − T R)⁻¹·P`: the rank-N form of the SAME series, and the
   docstring says so explicitly ("the rank-N analog of Hébert's
   `(1 − P_ss)⁻¹` factor", `geometry.py:2311-2313`; "at `n_modes = 1`,
   `T₀₀ = P_ss` exactly", `geometry.py:2314-2318`).
4. **`orpheus/derivations/continuous/peierls_nystrom/origins/specular/continuous_mu.py:146`**
   — `T_mu = 1/(1 − exp(−2aµ))`: the continuous-µ closed form of the same sum.

Item 3's docstring *proves* items 2 and 3 are the same operator at rank 1.
Item 1 is the same construction one bounce deep. The unifying concept is
already named — `orpheus/derivations/continuous/trajectory_resolvent/billiard.py:14-31`
calls it the Birkhoff transfer-operator resolvent — and the facade owns none
of the four implementations.

### TWIN 5 — the axial-quotient map (`r = |x − c|` + region bracket)

- **`orpheus/mc/solver.py:74-81`** `ConcentricPinCell.material_id_at` —
  `r = sqrt((x−c)² + (y−c)²)`, then a linear scan over `radii`.
- **`orpheus/mc/solver.py:186-195`** `MCMesh.material_id_at` — same radius,
  then `np.searchsorted(self._edges, pos)`.
- **`orpheus/moc/geometry.py:155-168`** `_identify_region` —
  `r = sqrt((x−cx)² + (y−cy)²)`, then a linear scan over `radii`
  with a `+1e-12` bias.

Same operation (project a 2-D point onto the orbit space of the axial rotation
group, then bracket it). Three implementations, three different tie-breaking
conventions (`<=` with no bias / `searchsorted(side="right")` / `<=` with
`+1e-12`). This is a *within-scope* duplicate — MC alone carries two of them.

### NON-TWINS worth stating (checked and rejected)

- **MC's `% pitch` (`mc/solver.py:417-418`) vs the mod-π wrap in
  `singular_eigenfunction/slab/one_group.py:198`.** Both quotient by a
  translation lattice, but different lattices for different reasons (spatial
  periodicity vs. `tan` periodicity). Same *mathematics*, not the same
  *operation*. No duplication finding.
- **`R_spec = ½M⁻¹` (moment space) vs an SN ordinate permutation.** Same
  physical law, structurally different objects (Galerkin projection vs. node
  permutation). Not a duplicate implementation.
- **`chord_half_lengths` (`derivations/common/kernels.py:52`) vs anything in
  `numerics/`.** It is a genuine single-source primitive already: `cp/solver.py:172`
  and the Peierls cylinder reference both import it. Correctly shared — the
  one place in this audit where the extraction already happened.

## The 7 specific questions

**Q1 — MoC reflective track linking: matrix, angle arithmetic, or index map?**
**Angle arithmetic + TWO nearest-neighbour searches, no matrix.** The reflection
is split into an angular half and a spatial half:

- angular: `orpheus/moc/geometry.py:222-229` — `phi_refl = np.pi - phi[i]`,
  two dead wrap branches (for the shipped set `φ ∈ (0,π)` strictly, so
  `π − φ ∈ (0,π)` and neither `if` can fire), then `argmin`.
- spatial: `orpheus/moc/geometry.py:412-435` `_find_link` — squared-distance
  `argmin` of the exit point against the candidate entry/exit points.
- the fwd/bwd flag: `orpheus/moc/geometry.py:232-234` `_is_vertical`, an
  integer set membership `surface in (1, 3)`.

**Is it the same operation the SN specular BC performs?** *Structurally yes,
implementationally no.* SN realizes the specular law as a first-class operator
sibling `B` (an `SNBoundaryOperator` produced by `SNBoundaryRealizer.realize`
over a `ReflectiveBoundary` law) acting on the trace field; MoC has no law
object, no operator, and no trace type — the reflection is baked into four
`int`/`bool` fields on `Track` (`moc/geometry.py:58-69`) at mesh-construction
time. MoC's BC registry (`moc/geometry.py:444-455`) has exactly one entry,
`"reflective"`, whose factory returns the string `"reflective"` and does
nothing else. **Note a real difference, not just a spelling one:** the SN
operator is exact; MoC's is a nearest-neighbour approximation (measured below).

**Q2 — MoC azimuthal angles: equispaced (roots of unity)? cos/sin on them?
mirror pairing?** Yes to all three, and none of the three is exploited.
Set: `orpheus/moc/quadrature.py:89`, exactly `2π(2k+1)/(4n_azi)` — the odd
`4n_azi`-th roots of unity, a free `C_{n_azi}` orbit half-step-offset off the
axis. `cos`/`sin` are evaluated at `orpheus/moc/geometry.py:319-320`. The
mirror pairing is **`k ↦ n_azi − 1 − k`**, i.e. `[::-1]` — a closed-form
permutation that `_reflected_azi_index` rediscovers by search on every call
(and is called twice with identical arguments at
`orpheus/moc/geometry.py:386` and `:393`).

**Q3 — MC direction sampling / scattering: rotation into a lab frame?**
**No rotation exists — there is nothing to rotate.** `orpheus/mc/solver.py:409-413`
re-samples a *fresh, absolute* direction at every real collision
(`if not virtual_collision: theta = π·u; phi = 2π·u`). Scattering is isotropic
in the lab frame by construction, so the classic "rotate (µ, φ) about the
incident direction" never arises: there is no incident-direction frame, no
rotation matrix, and no trig identity for one. (The non-isotropy of
`theta = π·u` is *already* catalogued as **ERR-018** and documented at
`docs/theory/methods/monte_carlo.rst:543-590` — not a new finding, and not a
transformation finding.)

**Q4 — MC surface reflection: `d' = d − 2(d·n)n`?** **MC has no surface
reflection at all.** `MCMesh.BC_REGISTRY` (`orpheus/mc/solver.py:209-211`)
contains exactly one entry, `"periodic"`. The boundary operation is the
translation `nx_ %= pitch; ny_ %= pitch` (`orpheus/mc/solver.py:417-418`) —
the deck transformation of the torus `ℝ²/pℤ²`, not a reflection. The
Householder form appears **once in the entire audited scope**, as prose in
`orpheus/derivations/continuous/peierls_nystrom/origins/specular/r_matrix.py:48-52`,
and is never coded.

**Q5 — CP / derivations chord geometry: symmetry reductions that are quotients?**
Yes, four, all implicit:

1. `orpheus/cp/solver.py:276-280` / `:353-357` — the **method of images**
   (`gap_c = bnd_pos[i] + bnd_pos[j]`, an addition where the direct term
   subtracts). Marked only by the comment "Reflected path (via centre
   symmetry plane)".
2. `orpheus/derivations/common/kernels.py:52-103` `chord_half_lengths` +
   `orpheus/cp/solver.py:329, 332, 359` — the chord is computed as a **half**
   and multiplied by 2; that factor 2 is the orbit size of the mirror through
   the chord's perpendicular bisector.
3. `orpheus/cp/solver.py:170` — the impact parameter runs on `mesh.edges`,
   i.e. `y ∈ [0, R]`: a `y → −y` quotient never stated anywhere.
4. `orpheus/derivations/common/quadrature_recipes.py:369-372`,
   `.../peierls_nystrom/origins/cylinder_g_bc_3d.py:64`,
   `.../peierls_nystrom/cylinder.py:43-45` — three prose statements of the
   azimuthal fold `∫₀^{2π} → 2∫₀^π`, one convention, no shared code.

No `abs()` on a coordinate is used as a fold in this scope — the folds are all
done by *choosing a half domain up front*, which is why they are invisible to
a grep for `abs(`.

**Q6 — Does ANY of these modules build a rotation or reflection MATRIX by hand?**
**No.** A repo-wide grep over `moc/ mc/ cp/ diffusion/ homogeneous/ derivations/`
for every rotation/reflection-matrix shape (`[[c, -s`, `[[cos`, `Matrix([[...cos`,
`eye(3) - 2`, `eye(2) - 2`, `- 2 * np.outer`, `- 2 * sp....outer`) returns
**zero hits**. The only hand-built orthogonal matrices in the project are in
`orpheus/numerics/symmetry.py` (`_rotation_z:1017`, `_reflections:1027`,
`_vertical_mirrors:1123`, `_octahedral_ops:1132`, `_icosahedral_ops:1157`,
`_rotation_about_axis:1217`). The closest thing in scope is
`orpheus/moc/geometry.py:322-327` and `:331-333`, which apply an SO(2) rotation
**component-wise, expanded by hand** (`-c[0]*sin_phi + c[1]*cos_phi`), and
`.../specular/r_matrix.py`, which builds a **Gram** matrix, not a rotation.

**Q7 — Any module computing "the permutation induced by a transformation on a
point set" with its own loop (duplicating `_orbit_closure`)?**
**Exactly two, both in MoC, and no others anywhere in the scope.**
`orpheus/moc/geometry.py:229` (angular) and `orpheus/moc/geometry.py:412-435`
(spatial). A grep for `argmin`/`best_dist`/`nearest` across the whole non-SN
scope returns nothing else structural — the other hits are `searchsorted` for
CDF sampling / region bracketing and eigenvalue-branch selection. See §TWIN 1.

## Measurements (probe scripts at `/tmp/probe_moc.py`, `/tmp/probe_moc2.py`)

**M1 — MoC's azimuthal set is roots of unity, and `roots_of_unity` fixes it.**
Over `n_azi ∈ {2,3,4,5,6,8,12,16,32,64}`:

- `phi == 2π(2k+1)/(4·n_azi)` to ≤1e-15 for every `n_azi`. ✔
- The mirror `k ↦ n_azi−1−k` (i.e. `cos → −cos`, `sin → sin`) is
  **bit-exact under `roots_of_unity` for every `n_azi` tested, and bit-exact
  under `linspace`+`cos` for NONE of them.**
- For **odd** `n_azi` there is a node exactly at `φ = π/2` (`2k+1 == n_azi`).
  `np.cos` returns `6.12e-17`; `roots_of_unity` returns exactly `0.0`. The
  vertical-track family currently survives only because the guard
  `abs(cos_phi) > 1e-15` at `orpheus/moc/geometry.py:115` happens to be
  looser than the error. It works by tolerance, not by construction.
- Node values differ by at most `5.0e-16` between the two routes, so a swap is
  a re-baseline, not a bit-identical change.

**M2 — `_reflected_azi_index` reproduces the closed form exactly.**
`[_reflected_azi_index(phi, i) for i in range(n)] == n−1−k` for every
`n_azi ∈ {2,3,4,5,6,8,12,16,32,64}`. The search is correct; it is just a search
for something that is already known.

**M3 — MoC's track link is a bijection today, but the geometric match is loose.**
Wigner-Seitz pin cell, `Mesh1D.from_geometry`, `bc_right=BC("reflective")`:

| `n_azi` | ray spacing | tracks | boundary slots | distinct targets | bijection? | **max link gap** |
|---|---|---|---|---|---|---|
| 8 | 0.05 | 740 | 1480 | 1480 | yes | **2.61e-02 cm** |
| 16 | 0.05 | 1476 | 2952 | 2952 | yes | **4.23e-02 cm** |
| 5 | 0.10 | 230 | 460 | 460 | yes | **8.96e-02 cm** |
| 4 | 0.20 | 96 | 192 | 192 | yes | **1.51e-02 cm** |

So the *missing bijectivity guard does not currently bite* — an honest
negative. But the reflection is **not geometrically exact**: the reflected
track's entry point sits up to `8.96e-02 cm` from the exit point, ~2.5 % of the
`3.6 cm` pitch. `_find_link` computes `best_dist` (`moc/geometry.py:422, 431-432`)
and **discards it** — nothing reports or bounds this. For comparison,
`_orbit_closure`'s window is `atol·100 = 1e-11` (`symmetry.py:1241, 1395`), nine
orders of magnitude tighter, and returns `None` rather than a wrong answer.
Corroborating the mirror structure: tracks-per-azimuth is symmetric under
`k ↦ n−1−k` in every case (e.g. `n_azi=16`: `[79,90,98,102,102,98,90,79,…]`).

**M4 — the existing MoC gate cannot see any of this.**
`tests/moc/test_verification.py:556-588` `test_reflective_links_form_cycles`
follows `fwd_link` and asserts `current in visited`. For **any** total map
`f: [0,n) → [0,n)` the orbit must repeat within `n+1 ≤ max_steps = 4n` steps —
so the cycle assertion is satisfiable by construction and can only fail on a
dangling `-1` link (which the loop's `assert current >= 0` already covers
separately). It also ignores `fwd_link_fwd`, so it does not test the
fwd/bwd map at all. It cannot detect a non-bijection, a large link gap, or a
wrong azimuthal partner.
